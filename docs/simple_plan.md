现在既然已经验证 LAS 和 3DGS 坐标能对上，那么之前最大的风险“点云轨迹和 3DGS 渲染坐标不一致”基本解除。这样一来，点云在 2.5D 障碍检测上比 3DGS 更适合。

**为什么点云更适合轨迹生成**
点云是扫描仪直接得到的几何采样，本质上更接近“真实物体表面”。你要做的是障碍检测、可通行区域、距离场、A*，这些都是几何任务，所以点云更自然。

3DGS 的优势是视觉渲染，不是几何规划。Gaussian 是椭球，有 opacity、scale、旋转、漂浮点和视角相关效果。它能把图渲染得像真实场景，但不一定是干净的物理障碍表达。用它投影做 occupancy，会更容易遇到虚假障碍、边缘膨胀、漂浮 Gaussian、玻璃/反光造成的噪声。

所以后续最好是：

```
LAS 点云 -> 2.5D 障碍图/ESDF/轨迹
3DGS PLY -> 沿轨迹渲染 RGB-D
```

这也和老师说的路线一致，而且不是粗糙妥协。你可以把它表述成：**点云提供几何先验，3DGS 提供视觉观测，两者在统一坐标系下耦合生成训练数据。**

**坐标系建议**
我建议后续统一使用 `yup` 作为你的工程内部坐标，因为你现在的 `render_one_view.py` 已经基于 `test1_yup.ply` 跑通了。

也就是：

```
内部坐标：Y-up 版本
现实竖直向上：-Y
地面平面：X-Z
高度：height = floor_y - y
```

如果 LAS 原始是 Z-up，就在读入 LAS 时转换：

```
x_yup = x_las
y_yup = -z_las
z_yup = y_las
```

不要为了点云去重写 `render_one_view.py`。渲染链路已经跑通，优先保持稳定。

**行动计划**

**1. 坐标统一**
先确定所有后续模块都吃同一种坐标。推荐统一成 `yup`。

输入：

```
test1-pointcloud-0704.las
test1_yup.ply
```

处理：

```
LAS 原始点 -> zup-to-yup -> 统一坐标点云
PLY 直接用 test1_yup.ply
```

之后所有轨迹点、相机位置、目标点都在 `yup` 坐标下表达。

**2. 估计地面高度**
不要手动假设地面就是 `y=0`，要从点云估计。

在 `yup` 里，竖直方向是 `-Y`，所以可以统计点云的 `y` 分布。地面通常对应一个很密集的水平面。

可以先用简单方法：

```
height_axis = -y
找低处大面积平面
得到 floor_y
```

更稳一点可以：

```
对点云做体素降采样
用 RANSAC 拟合水平地面平面
得到 floor_y 或 floor plane
```

第一版不必太复杂，先用直方图找地面峰值就够验证。

**3. 设定机器人参数**
建议先固定，不要一开始就随机：

```
机器人半径 rb = 0.25 m
机器人高度 hb = 0.8 m
地面过滤 margin = 0.05 m 或 0.08 m
地图分辨率 = 0.05 m 或 0.1 m
```

NavDP 论文里机器人高度随机是为了数据多样性；你第一阶段先固定高度，跑通数据引擎更重要。

**4. 截取机器人高度范围**
这是 2.5D 的关键。

在 `yup` 坐标中，高度可以定义为：

```
h = floor_y - y
```

保留障碍候选点：

```
margin <= h <= hb
```

也就是只考虑机器人身体会撞到的高度范围。

这样可以排除：

```
地面点
天花板
高处灯具
拱门上沿
高处装饰
```

但会保留：

```
墙
桌腿
椅子
柜子
低矮障碍
门框下部
机器人高度内的横梁
```

**5. 投影到 X-Z 平面**
把高度截取后的点投影：

```
grid_x = x
grid_z = z
```

得到 2D occupancy grid。

每个格子只要有足够数量的点，就标为障碍。这里不要用“有一个点就算障碍”，否则噪声太多。建议：

```
每个格子点数 >= 2 或 3 才算障碍
```

如果点云很密，可以阈值更高一点。

**6. 清理障碍图**
对 occupancy map 做后处理：

```
去掉小连通域
形态学 opening 去孤立噪声
形态学 closing 补墙面小洞
```

这一步很重要。点云投影会有空洞和毛刺，不清理的话 A* 会走进奇怪的小缝。

**7. 机器人半径膨胀**
把障碍区域按机器人半径膨胀：

```
膨胀半径 = rb / grid_resolution
```

比如：

```
rb = 0.25 m
resolution = 0.05 m
膨胀 5 个格子
```

膨胀后的障碍图才是真正给 A* 用的不可通行区域。

**8. 计算 2D ESDF / distance transform**
对未膨胀或已膨胀的障碍图计算距离场。

推荐保留两份：

```
raw_distance_map：原始障碍距离，用于评价离障碍多远
planning_obstacle_map：膨胀后的障碍，用于 A*
```

这样轨迹不会碰撞，同时还能用距离场把轨迹往空旷地方推。

**9. 采样起点终点**
起点终点必须满足：

```
在自由区域
离障碍距离 > rb + safety_margin
两点距离不能太近
A* 可连通
```

第一版可以人工指定几个点验证，不要一开始随机生成大规模数据。

**10. A\* 生成路径**
在 2D grid 上跑 A*。

代价可以先简单：

```
普通长度代价 + 距离障碍惩罚
```

比如离障碍越近，代价越高。这样路径会自然远离墙和桌椅。

**11. 路径优化和平滑**
A* 出来的路径会锯齿状。后处理建议：

```
路径抽稀
shortcut 检查
三次样条插值
重新碰撞检查
```

注意：**平滑后一定要重新碰撞检测**。样条可能把路径拉进障碍物。

**12. 轨迹转相机位姿并渲染**
对平滑轨迹上的每个点：

```
相机位置 = 机器人位置 + 相机高度偏移
朝向 = 轨迹切线方向
up_axis = -y
```

然后用 `test1_yup.ply` 渲染 RGB-D。

最终数据就是：

```
trajectory.json
rgb frames
depth frames
pointgoal / local waypoints
ESDF score / collision label
```

**最终推荐路线**
你可以和老师这样讲：

```
我们用点云生成几何可通行图，因为点云更适合障碍检测；
用 3DGS 沿轨迹渲染视觉数据，因为 3DGS 更适合生成 RGB-D；
两者坐标已验证可对齐，因此这条路线比单独用 3DGS 做几何规划更稳。
```

这条路线技术上更稳，也更容易解释。你之前担心 2D 投影太粗糙，其实可以通过“高度截取 + 膨胀 + 距离场 + 平滑后碰撞复检”把它做得很科学。
